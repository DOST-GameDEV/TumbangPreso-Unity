# LAN discovery when host broadcasts do not reach the browser

Original8db and corrected917 packages reproduce the same direction: a PC-hosted
room is absent from the laptop's natural LAN list and its code says No game
answered. Direct address joins2/4Ready. Reversed roles discover and code-join
normally. An independent unused-port diagnostic sends three broadcast variants
and one unicast packet; only unicast reaches the laptop. Unity's endpoint list
includes the physical subnet and Send accepts each destination. These facts
narrow delivery direction; they do not prove an OS/firewall cause.

The change keeps passive adverts and their payload format. While browsing, the
existing8911 listener sends a small query. A live advertising host queues its
observed requester endpoint then answers with the current ordinary advertisement
by unicast. Hosts open their responder listener but do not solicit. Replies are
limited per endpoint and the cache is bounded; different browsers can receive
replies during the same interval. Stop/replacement retires requests and responder
state. Browsing leases are refreshed by the visible LAN view and code lookup.
There is no subnet scan, extra service, Windows setting or gameplay-wire change.
Existing LAN visibility/advert eligibility is preserved; Relay does not advertise
or answer this path. This does not change host authority or seat admission.

Original owned-socket baseline has one request/reply failure and five controls
passing. Corrected candidate passes eight cases including two new multiple-client
and stopped-request controls; two additional scoped boundary cases pass for
repeated requester throttling and retired listener handling. No unchanged eight-
case rerun. The initial candidate had a shadowed-variable compiler error and ran
ZEROcases; it is preserved separately and supplies no behavior proof.
