## Confirmed source gap: LAN directory row

`HubJoin` builds a LAN row from `Hub.Host.Rooms(lan:true)` with both `Name = entry.HostName` and `Key = address:port`, but its JOIN callback passes only `Key` to `Hub.Host.Join` (`UI/ConvertedMatchSetup.Hub.cs:320-343`, `UI/Hub/HubCustom.cs:279-305`). `ConvertedMatchSetup.Join` calls `LeaveRoom` before awaiting the join; `LeaveRoom` invokes `NetSession.Stop`, and `StopCurrentTransport` calls `LanBeacon.StopAll`, which clears `_seen` (`ConvertedMatchSetup.Hub.cs:163-193`, `NetSession.cs:1300-1342`, `LanBeacon.cs:240-263`). `LobbyJoinPanel.Connect` sees `address:port` and takes the direct-address branch, which never resolves or stores a room name (`LobbyJoinPanel.cs:872-895`; native join delegates to that branch in `LobbyJoinPanel.Native.cs:124-142`). The displayed LAN row's title is therefore dropped on the way into a successful room.

On the client, `ConvertedMatchSetup.RoomTitle` first reads the host-only static `NetSession.RoomTitle` (cleared by `LeaveRoom`), then searches current `Query.Servers` or `Beacon.SortedEntries` by the seated `RoomCode`, and otherwise returns empty (`ConvertedMatchSetup.Hub.cs:205-222`). `MatchRpc.SendSeating/OnSeatingMsg` delivers the join code but no room title (`Net/MatchRpc.cs:924-945,1008-1043`). `HubLobby.Draw` substitutes `LOBBY` when that getter is empty (`UI/Hub/HubCustom.cs:473-481`). No title remains for a LAN-row direct-address join after its pre-join beacon clear, despite the client having shown the correct title in the directory. This is a data-lifetime defect, not evidence that the host field was uneditable.

## Other routes, kept distinct

- A user typing a bare direct address has no title source before connection. The generic `LOBBY` heading is expected under the current no-title-on-seating contract; do not label that alone a regression.
- A LAN **code** join runs `ResolveCodeAsync`, which restarts beacon listening and obtains `ResolvedMatch.HostName` after the initial `LeaveRoom`; `StartClientAsync` does not itself clear the beacon in a settled session (`ServerQuery.cs:345-390`, `LobbyJoinPanel.cs:898-933`, `NetSession.cs:1039-1059`). As long as fresh beacons keep arriving, the getter can find the title. It is not proven to lose the name on an ordinary code join. A later `StopAll`, failed discovery, or entry expiry (4 s) leaves no durable client copy (`LanBeacon.cs:588-610`).
- An online code lookup also obtains `ResolvedMatch.HostName`, but does not store it. The getter can still find a matching current `Query.Servers` entry because browsing remains active and `StopCurrentTransport` does not clear that query. It is not guaranteed: the browser retains only the current query results and removes absent entries, while code resolution can find a room outside that browsed set (`ServerQuery.cs:166-191,226-327,345-443`). A joined client's heading can therefore depend on a mutable discovery list. Reconnect/direct-address paths repeat the same absence of a durable joined-title copy. This is a conditional lifetime risk, not a demonstrated online failure.

## Narrow repro before any fix

Use two isolated local player profiles and one LAN host with a distinctive room title; do not involve UGS. On the joining process, open the LAN directory and capture the row's displayed name/key and `LanBeacon.SortedEntries` count, press that row's JOIN, then after seating capture `NetSession.RoomTitle`, `LobbySession.JoinCode`, `ConvertedMatchSetup.RoomTitle`, the `HubLobby` heading and beacon entry count. Expect the directory name to be nonempty before JOIN but the joined heading to read generic `LOBBY` while the room code and connection are valid. Repeat as a **code** join as the comparison: it should take `ResolveCodeAsync` and may retain a fresh beacon entry. This is a route/lifetime check, not an OS typing check. Preserve the current wire format; no protocol change or speculative title fix is proposed from this source read alone.
