# Practice Tansan eligibility, 2026-09-27

QA-16 investigation and local source correction. No live wallet, balance, history, deployment or user profile was changed.

## Reproduction path and cause

`ConvertedMatchSetup.Hub.cs:82-97` starts Practice after leaving any room, then starts an offline match against bots. Guided training also sets `SceneFlow.Networked = false` (`SceneFlow.cs:608-617`); `PracticeSandbox.Allowed` is offline-only (`PracticeSandbox.cs:64-78`). `MatchStatsCollector.BeginMatch` captures only the ruleset name, `Classic` or `HeroStrike` (`MatchStatsCollector.cs:247-266`). At a finished match it creates a valid `MatchRecord` with a new ID, UTC timestamp and a non-bot local human line; `Online` is set from the transport's state **at the end** (`MatchStatsCollector.cs:414-459`). Practice can therefore produce a normal-looking offline record.

`MatchStatsCollector.Adopt` passes that record to `CareerStore.Record` (`MatchStatsCollector.cs:471-485`). `CareerStore.Record` checks for an ID and a human line, applies local career progression, remembers history and queues an upload when newly applied (`CareerStore.cs:379-421`). `MatchRecordRules.Submittable` checks ID and human line but not `Online` (`MatchRecord.cs:458-463`); `match-record.js` normalises `Online` but its submit path also checks only sanity and the submitting human line before applying career state and storing history (`match-record.js:97-174,1057-1100,1191-1194`). Neither path makes Practice ineligible.

The actual balance writer is `ugs/cloud-code/wallet.js`. Every wallet action reads server `matchHistory`, converts each record in `earnedFrom`, settles unseen IDs and returns `paid` (`wallet.js:139-179,263-282,314-319`). `earnedFrom` accepts a valid ID, non-bot player ID and parseable `PlayedUtc`; it does not inspect `Online`. The C# mirror `EconomyRules.TryRead` has the same omission (`Economy.cs:451-478`). Its `Settle` pays completion and placement for any non-AFK earned match, and `Count` can use the same practice record to advance claimable tasks (`Economy.cs:277-311,390-417`). This explains an actual Tansan grant if the practice record reaches cloud history and the player later opens a wallet surface while signed in.

`PLAYTEST_TOPUP = 999999` is a separate temporary owner-deployed grant in `wallet.js:35-40,279-282`. It raises a loaded wallet to that floor even when `paid == 0`. `WalletStore.LastPaid` comes from the Cloud Code `paid` response, while the cached balance is overwritten with the returned protected wallet (`WalletStore.cs:235-249`). `MatchResult` draws `CareerStore.LastAward`, which is local optimistic XP, not a Tansan payment (`MatchResult.cs:51-63,354-381`). A test must inspect `paid`, `EarnedToday`, `PaidMatchIds`, protected balance and the local result award separately; a rise to 999999 alone cannot prove practice settlement.

## Existing eligibility contract

`MatchRecord.Online` already means the match ran over Relay or LAN (`MatchRecord.cs:184-185`). `Mode` is only the ruleset, so Practice can be Classic or Hero Strike. `Ranked=false` is shared by eligible casual and LAN rooms. One non-bot human line exists in Practice and in legitimate rooms. The intended product copy says Practice records nothing (`HubModeSelect.cs:47-49`), while the economy design says only the server writes Tansan and LAN must remain playable (`front-end-flow-2026-09-23/ux1-plan.md:137-156`). The current Practice and training routes are offline; `Online` is the smallest existing record field that separates them from Relay/LAN without excluding casual or ranked matches.

One timing hazard needs care: `StartPractice` stops the old room and immediately starts scene loading, while NGO shutdown may remain `IsListening` until a later frame. The collector should capture eligibility from the *chosen route* at match start (`SceneFlow.Networked`, plus transport state as appropriate), then write the existing `Online` field from that captured answer. Reading `NetAuthority.IsNetworked` only at match end can also turn a legitimate LAN result false if its transport drops just before the whistle. No new MatchRecord field or historical rewrite is needed.

## Smallest correction to review

1. At the start of a match, capture whether it entered through a real networked room; write the existing `MatchRecord.Online` from that stable start decision. Practice, guided training and offline sandbox must remain false. Keep Relay/LAN casual, ranked and custom rooms eligible, including bot-filled legitimate rooms.
2. In `CareerStore.Record`, clear `LastAward` and skip local profile application, history insertion and upload queueing for a new `Online=false` practice/training result. `MatchStatsCollector.Last` may still serve the immediate result screen. Do not delete or rewrite existing career history or balances.
3. In `match-record.js` submit, treat an offline record from an old client/queued file as a successful no-op (`applied:false`) before profile, rating or history writes, so one permanently refused old practice record cannot block the next legitimate upload. Preserve the existing profile in the response and the duplicate-ID behavior for eligible matches.
4. In both `EconomyRules.TryRead` and `wallet.js earnedFrom`, reject records whose existing `Online` field is false before they become `EarnedMatch` inputs. This prevents unpaid historical practice records already in cloud history from paying on a future wallet load or contributing to claimable task progress. Existing paid balances are not clawed back. Leave `PLAYTEST_TOPUP` unchanged; the owner alone controls its deployment and later removal.

`Online` is host-authored and is not currently included in the match digest (`Integrity.cs:139-149`, `match-record.js:492-503`). The proposal fixes the normal Practice route and old unpaid offline records; it is not a claim that a modified client cannot forge an online record. Solving that stronger trust problem would need a separate transport/session proof, outside this QA correction.

## Implemented and verified locally

The C# `EconomyRules.TryRead` and JavaScript `earnedFrom` exclude old offline records from settlement and task input. `match-record.js` answers a queued old offline submit with a non-error `applied:false` result before protected profile/history mutation. `PLAYTEST_TOPUP` remains 999999 in source and was not deployed or changed. ## Result-copy follow-up

An offline Practice result could still inherit the sentence `SAVED ON THIS MACHINE, WILL UPLOAD` when an older online match was queued: `MatchResult.OnRecordReady` read the career's total queued count without asking whether the current record was eligible. `MatchResult.UploadCopyFor` now adds that sentence only when the current record is `Online` and the queue is nonempty. The result's stats and prior queue remain unchanged; no career, XP, Tansan, wallet or Cloud Code rule changed in this follow-up.

The existing result fixture gained the pure decision case `PracticeSummaryDoesNotClaimAnOlderQueuedMatchWillUpload`: a prior queued online record plus a current offline Practice record yields no upload copy; a current online record with that queue does, while online with an empty queue and null input do not. It does not instantiate or mutate a live CareerStore, submit a record, or claim that an actual results board was inspected.
