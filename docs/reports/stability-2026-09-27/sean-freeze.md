# QA-15: Sean cannot move after Cheska's ultimate

Initial source investigation at `04886cc4`, followed by an opt-in diagnostic implementation. The tester's sentence does not say which process observed Sean, whether he was the owning player or a bot, how long the stop lasted, or whether another status or pause was present. The cause remains unconfirmed. No two-player diagnostic run has occurred, and no gameplay fix is claimed. Line references below describe the inspected revision and may move as shared networking changes.

The proposed `cheska-sean` branch is now authored in `NetIceProbe.cs` and
`tools/net_ice_review.py`. It uses isolated profiles, two players, impact-anchored
CSV evaluation and bounded process cleanup. It is opt-in and native-unrun.
The detailed design below is preserved as rationale, not an instruction to add a
duplicate probe. The controlled axis does not exercise PlayerInputReader, a
physical device or Sean's AI; those interpretations of QA-15 remain open.

## Expected control path

Cheska's ABSOLUTE ZERO begins after the shared ultimate introduction. On the host, it gives every other player an Ice stun for `StatusRules.FrozenSeconds` (2.5 s) and Chilled for the freeze plus `StatusRules.ChilledSeconds` (5 more seconds) (`CheskaHeroKit.cs:155-176`, `RosterReworkRules.cs`). Chilled is a half-speed multiplier, not an action lock (`CharacterMotor.Status.cs:76-78`). The visual ice prison has no collider and shatters when the stun ends or its timer expires (`HeroHazards.cs:4197-4242`; existing `CheskaIceContractProbe` asserts no collider).

The report may describe the intended 2.5-second Frozen window rather than a lasting defect: the freeze starts **after** the shared introduction, so the button press to first movement includes both the authored introduction and the stun. The first reproduction must timestamp the actual impact and the first attempted movement, then ask whether Sean is still unable to move beyond the impact plus 2.5 s (allowing normal frame/network tolerance). A short stop inside that window is the kit contract; do not remove it to make a vague report disappear.

`SharedUltimatePhase.Accept/Receive` calls `PresentationClock.Hold`; `CharacterMotor.FixedUpdate` returns while held, and both status timers stop advancing with scaled time (`SharedUltimatePhase.cs:100-130`, `CharacterMotor.cs:796-799,2046-2050`). `SharedUltimatePhase.LateUpdate` completes or cancels on the phase deadline and `PresentationClock.Release` restores the requested scale (`SharedUltimatePhase.cs:171-230`). The installed NGO network time advances from unscaled delta (`Library/PackageCache/com.unity.netcode.gameobjects@d43d28498f17/Runtime/Timing/NetworkTimeSystem.cs:151-172`), so `Time.timeScale = 0` alone does not stop that deadline. On teardown, `SharedUltimatePhase.OnDisable/OnDestroy` cancels the hold; `NetSession.StopCurrentTransport` also requests scale 1 (`SharedUltimatePhase.cs:229-230`, `NetSession.cs:1347`).

Once the phase releases, `CharacterMotor.Update` decrements `_stunLeft` and `ClearStun` clears the element and total at zero (`CharacterMotor.cs:2094-2103,1670-1683`). Host and owning client can mutate their body; an observing client cannot clear metadata locally, but `IsStunned` reads the timer and falls false at zero (`CharacterMotor.cs:1103-1110,1529-1531`). `CanMove` reads only stun/trip and Rooted; it deliberately ignores `RoundActive` so players can walk in the warmup buffer (`CharacterMotor.cs:1499-1531`). The input reader writes the movement axis every update unless chat takes input; shared-phase `ClearActions` requires fresh *verbs* but does not park movement (`PlayerInputReader.cs:201-281`, `SharedUltimatePhase.cs:145-163`, `InputIntent.cs:52-56,217`). Sean's FLAME RUSH applies an impulse and leaves a trail; its end path clears the trail/aura, and `ApplyStagger` releases movement commitment (`SeanHeroKit.cs:126-156,298-312`, `CharacterMotor.cs:1818-1829`). No Sean-specific permanent movement gate is visible on this path.

For a remote-owned Sean, the owner submits movement on each physics step, including zero movement while stunned. The host validates the seat and movement, applies the pose, and relays `SyncUnit` with stun, trip, chilled/rooted, recovery episode and a monotonic pose serial (`CharacterMotor.cs:1027-1059`, `MatchRpc.cs:2261-2315,2334-2393`). The client validates host sender, epoch and serial before applying those timers (`MatchRpc.cs:2396-2481`). The host's 5 Hz match snapshot does not itself carry the motor's stun (`MatchRpc.cs:624-645`); the ordinary remote-owner `SubmitMove`/`SyncUnit` loop and a full world snapshot carry it. This matters if the owner's physics loop or ownership is already stopped.

## Ranked hypotheses and disproofs

1. **Sean owner's process remains held or at zero scale after the introduction.** This directly stops physics movement and timer decay at once. The code has a deadline and teardown release, and existing shared-phase tests check local release, so this is a high-impact but unproven timing/phase failure. Prediction: owner `Time.timeScale == 0`, `PresentationClock.Held` or `BlocksInput` remains true, and `StunLeft` stays constant after `SharedUltimatePhase.Now - Began` exceeds its duration. If all peers share it, inspect host pause/requested scale; if only Sean's process does, inspect phase receipt and local scene/kit preparation. A spectator-requested zero scale would be intentional pause, not a stuck phase.
2. **A newer host pose repeatedly restores a positive stun, or the host never releases its stun.** `ApplyNetworkState` overwrites the owner's timer from each accepted `SyncUnit` (`CharacterMotor.cs:1918-1951`); serial ordering prevents an *older* pose from arriving afterward (`MatchRpc.cs:2460-2464`). Prediction: owner's `StunLeft` sawtooths upward on incoming pose serials, with the host's `StunLeft` also positive or a second Cheska activation. If host reaches zero and owner falls monotonically to zero, this hypothesis is contradicted. `ChilledLeft` alone cannot explain no movement; its speed scale remains positive.
3. **Status expires but Sean's input or simulation ownership stays closed.** `CanMove` can be true while `Intent.Parked` zeros `MoveAxis`, the reader is disabled, or `IsLocallySimulated` is false because `NetAuthority.LocalSlot` no longer matches Sean's body (`InputIntent.cs:127,217`, `CharacterMotor.cs:1095-1110`). The shared ultimate does not itself set `Parked`; role snapshots update `IsDefender`/`RoundActive`, and neither is a `CanMove` gate (`RoundDirector.cs:143-220`). Prediction: host/owner stun and phase are clear, but the Sean owner has raw move input with zero `MoveAxis`, no active reader, or a slot/ownership mismatch. This is plausible if the tester meant only Sean, but would be coincident with the ultimate until reproduced.
4. **Sean moves on his owner but appears stationary on another machine.** This is a replication symptom, distinct from frozen input. Prediction: owner position advances and `CanMove` is true while host/observer position does not; inspect `SubmitMove` sender-seat, epoch, `AcceptMove` rejection and `SyncUnit` serials (`MatchRpc.cs:2261-2315`). If owner position itself does not advance, this branch is contradicted.

The ice-prison geometry, Chilled multiplier, `RoundActive` and Sean's FLAME RUSH trail do not currently provide a static explanation for a lasting movement stop. A disconnect should trigger session teardown and scene exit rather than leave an arena active; if a disconnect is part of the reproduction, record it as a separate transition before changing stun logic. There is no evidence yet to justify removing authority guards or forcing a blanket `ClearStun`.

## Smallest discriminating check

Extend the existing `tools/net_ice_review.py` runner with one `--case cheska-sean` branch. Keep its isolated named-profile backup/restore, optional link delay, two startup waits, process timeout/cleanup and shared `wallTime` CSV convention; launch only `host` and `owner`, not `observer`, and give this branch its own two-file evaluator rather than passing it through the current three-peer sheet/wall assertions. `Assets/TumbangPreso/Runtime/Diagnostics/NetIceProbe.cs` already receives `-tp-icecase` and `-tp-icetrace`; add an early case branch in `Configure`/`Update` and a separate compact CSV header so the existing ice cases remain untouched. The current case hardcodes Cheska on owner seat 1, disables every `PlayerInputReader`, and tests ordinary ice skills, so its present trace cannot establish QA-15.

In the new branch, set host seat 0 to Cheska and remote owner seat 1 to Sean through the existing lobby-pick RPC/sync pattern, wait for both bodies and the ready gate, disable AI and human readers only for deterministic probe control, park other bodies, and give Cheska exactly one ultimate charge. Trigger one host `Verb.Ultimate` via the existing `Intent.Set`/`BufferPress` pattern used by `NetUltimatePhaseProbe.cs`. The owner drives Sean's `Intent.Move` forward through impact and thaw, then briefly releases/represses after the expected freeze; no change to gameplay timers or authority. This controlled axis tests the motor/network gate, **not** a physical keyboard or `PlayerInputReader` route. If the controlled case passes but the player report persists, follow with a separate input-device reproduction instead of calling the report resolved.

At 20 Hz on both peers, trace only shared wall/server time; local and Sean slots; phase active/age/duration, `PresentationClock.Held` and `Time.timeScale`; Sean `StunLeft`, `TripLeft`, `RootedLeft`, `ChilledLeft`, `CanMove`, `IsLocallySimulated`, `Intent.Parked`/`MoveAxis`, and x/z position. Mark impact by the host's first positive Sean `StunLeft`, not by button press; finish at impact plus roughly five seconds (with a hard overall timeout). Evaluate that the introduction releases on both peers, owner/host stun returns to zero after the intended 2.5 s plus tolerance, and Sean advances on both peers under a nonzero controlled axis. The trace then distinguishes a stuck hold, repeated positive stun, a local intent/ownership gate, and owner-only motion. Only if the latter occurs should a second pass add `SubmitMove` rejection reason and pose serial instrumentation; those are not needed in the first trace. A third observer is likewise conditional.

Existing `SharedUltimatePhaseTests` checks introduction release but not a frozen victim's return to movement; `CheskaIceContractProbe` checks local escape/visual removal; `StunFrostTests` checks offline tag frost. None establishes QA-15 on Sean's owning peer. After the trace identifies a branch, add one focused regression against that exact transition and rerun the same two-process case. No host-only pass can close this report. This is an implemented but unrun reproduction diagnostic, not proof of a defect or fix.
